# Changelog - every release

The plugin's own `readme.txt` carries only the most recent entries: WordPress.org truncates that
section at 5000 characters, and a changelog the directory cuts in half is worse than a short one
that points here. Nothing is lost - this file is the full history.

## 0.4.10
* Fixed: **the shipping price shown before a town is picked no longer reads about 20% low for a courier that charges its own VAT**, on a shop WooCommerce works out no shipping tax for. That pre-town price is a cached copy of the courier's own live quote, and it kept only the price and dropped the tax - so a courier that reports its VAT (Speedy, Express One) or has it added (Sameday) showed the net figure until a town was chosen, then jumped to the gross figure the customer is actually charged. The reference now keeps the tax the quote already worked out, so the before and after agree. A shop that does add shipping tax was never affected (WooCommerce puts the tax on either figure), and the exact price once a town is chosen was always right - only the estimate before it was low.
* Added: **the map shows which Sameday easyBox lockers are full and greys them out, kept live.** Sameday is the only courier whose locker list reports its free compartments, so for its easyBoxes the map now knows whether a parcel can still go in. A full one is greyed and marked "Full" - on the pin, in the list and in its popup, where it can no longer be chosen. "Full" means no free compartment of a size the shop's parcel fits: an easyBox has small, medium and large compartments, a small parcel fits any of them and a large one only a large, so the check follows the shop's own parcel size. The map re-asks once a minute in the background, so a locker that fills while the customer is looking greys itself with no reload and no freeze. The checkout's own automat dropdown greys and disables a full easyBox the same way, so the customer sees the same answer whether they pick a locker from the map or straight from the dropdown. Staffed "Sameday point" counters, which have no compartments to fill, are never marked full. Only Sameday: no other courier's API reports this (BOX NOW shows it only inside its own map widget, which this plugin does not use).
* Fixed: **the address map shows a delivery as free once the order has earned free shipping, exactly as the checkout row does.** The map advertises a price per office to help the customer pick a pickup point, and it is fed from the same pricing as the shipping row so the two can never disagree - except it never checked the free-shipping threshold. A shop that gives free delivery over an amount showed the courier's ordinary per-office price all over the map, on every office and every locker, while the row beside it charged nothing. Every delivery point that has earned free delivery now shows the shop's free-shipping label (or a zero price where none is set), the way the row shows it. Both the cached reference the map opens on and the live figure that replaces it apply this one rule through a single presenter, so a free option reads the same on both; the paid reference number itself is unchanged. Nothing changes for a shop that sets no free-shipping threshold.
* Fixed: **the checkout block's street/town/postcode hide (and its required phone) now hold on the Store API too, whenever another plugin reads the country locale early.** 0.4.9 closed this hole on the block PAGE - the GET that decides what the block shows - by working the checkout out from the requested URL when the main query is not ready. The order-placement path had the same hole one layer down: the hide and the required phone recognised the Store API request (the POST that validates and places the order) by a constant, REST_REQUEST, that WordPress does not define until parse_request. A plugin that read the locale on an earlier hook had the fields decided before that constant was set, WooCommerce cached the wrong answer for the whole request, and the Store API could then require WooCommerce's own street, town and postcode on an order the block never showed them on - a refused order, not a doubled field. The Store API request is recognised from its URL now (the REST prefix or ?rest_route=, so a renamed prefix and a plain-permalink shop are both covered), so the answer is the same whenever it is read. The block page and the Store API share one check (an internal tidy: the two copies that had drifted apart are one helper), and the URL test is tighter than the text-match it replaces, so a front-end URL that merely carries "/wc/store/" in a redirect argument is no longer taken for the Store API.

## 0.4.9
* Added: **the waybill on the order screen and in the orders list says when it is out of date, and when it still needs printing.** It now carries a state: RED when the order changed after the waybill was issued (the amount or the address) and nothing re-issued it - auto re-issue is off, or the courier already holds the parcel, or the change came from outside the order screen (a payment gateway, an automation) where the re-issue hook never fires. It is read from the order as it stands, so it catches the change however it arrived - a Sameday order edited after its waybill printed the old sum showed nothing before. GREEN while the current waybill has not been printed yet - a fresh auto-label, an automatic re-issue, or one made by hand and not opened; printing it by any route clears the green, re-issuing clears the red. (The automatic re-issue on an amount or address change was already there behind "Re-issue the waybill when the order changes" in the settings; this adds the half the merchant can see - what happened when it did, or when it could not.) A waybill the courier has already collected stays flagged red until it is dealt with, keeping the one-time "arrange the change with the courier" note.
* Fixed: **a Speedy address on a street that shares its name with another is no longer refused at the packing table.** Sofia has a бул. ВИТОША and a ул. ВИТОША. The checkout offered both off Speedy's own list - and to the street box they were one entry: whichever the customer clicked, the box kept the first, and once one was chosen a click on the other merely closed the list. The order then carried "ВИТОША" alone, and Speedy refuses a bare name in a town where it is not unique (measured 2026-09-13 against Speedy's address validation: "За избраното населено място се изисква ул./бул. от номенклатура"; ЧЕРНИ ВРЪХ, ЕВЛОГИ ГЕОРГИЕВ and every other doubled name the same, ЦАРИГРАДСКО ШОСЕ and every unique name fine). The two are two entries now, the box shows the one that was chosen, and the order carries Speedy's own id for it and its type beside the name - the waybill goes by the id (proved on the live account: waybill 63740770880 to ул. ВИТОША 10, voided again). An order from before, a typed street or one taken off the map still names the street only; at label time Speedy's list is asked once, one street of that name gives its id, and two with nothing to tell them apart are refused on the order screen with both spelled out, instead of by Speedy. The same id reaches Pigeon Express, whose API had a field for it that was never filled. The order editor shows the type too - it listed both ВИТОША rows as "ВИТОША" and "ВИТОША" - and the order's own address line, the one on the invoice and the customer's order page, reads "ул. ВИТОША 10" rather than "ВИТОША 10".
* Fixed: **Express One and Европът send the parcel to the street the customer picked, not the first of that name.** Express One lists three "ВИТОША" in Sofia (БУЛ., КВ., УЛ.) and Европът four (бул., кв., ул., жк.); both matched the order's street by name at label time and took the first hit with a note saying so - a customer who chose ул. ВИТОША got a waybill to бул. ВИТОША. The street's own id, now on the order, settles it; the type alone narrows several of a name to the ones of that type; a bare name behaves as before. An id off another courier's list is ignored.
* Fixed: **a Pigeon Express street with a name can be found in a big town.** Pigeon's street list is paginated at 100 a page and the search read the first page only - for Sofia, a hundred numbered streets out of 4657 on 47 pages (measured 2026-09-13), so no customer could find Витоша or Шипка with Pigeon. The term goes to Pigeon as its `name` filter and the pages it answers with are read. And for every courier the street box now lists the streets that begin with what was typed first, then those with a word that does, then the rest: Pigeon's answer for "Витоша" opened with thirty-one numbered streets ("улица 600-НА (ВИТОША)") and had улица Витоша and булевард ВИТОША at positions 32 and 33, past the twenty the box shows.
* Fixed: **a street chosen on the address map is a street off the courier's list.** The map wrote whatever its reverse geocoding answered straight into the street box - "бул. Княз Александър Дондуков" for one point, "Кърниградска" for the next (Sofia, measured 2026-09-13) - and Speedy's street search answers the typed form with nothing at all, so a Speedy order placed off the map in a town with two streets of that name reached the packing table with a street Speedy refuses; Express One and Европът refuse any street that is not off their list. The map now asks the list which street that is and the box holds it with its id and type; a street the list does not have stays as text for a courier that takes one, and for a courier that lists its streets the box is left for the customer to fill, with a note under it saying which street was not found and the field marked the way a refused one is. At label time every courier now reads a street written with its type in front the same way ("булевард „Витоша“" is бул. ВИТОША), so orders already placed off the map resolve too.
* Changed: the orders list and the order screen say "unchanged for 9 days" about a shipment's status, not "updated 9 days ago" - the stamp is the last time the courier's answer changed, and a parcel held at "information received" for nine days read as a tracking poll that had stopped.
* Fixed: **on the checkout block, the courier pickers came back to life after a tab click, and the rates re-priced.** Every delivery change - the type, the town, the office - asks the checkout to recalculate; the classic checkout re-renders and hands the pickers back, the block did neither: from the first tab click the pickers stayed greyed out and dead, and the rates stayed priced for the old selection. The combined map was the only way through. The block now asks the Store API to recalculate and the pickers follow.
* Fixed: **the cart block, and a checkout block nobody had touched yet, showed the order's refusals as a red banner.** "Please enter a phone number" and "please choose your Speedy delivery point before placing the order" were painted over a cart the customer had only opened - the plugin answered the Store API's validation on every cart read. It answers when the order is placed now, as the classic checkout does.
* Fixed: **on the checkout block, a delivery in the order total showed the prepaid price after cash on delivery was chosen.** The collection fee is in the courier's quote and the order did charge it (2,41 € for a Sofia office with 30 € to collect), but the rate row went on saying 2,12 € - the block never re-priced its rates when the payment method changed. It asks for a recalculation now, with the payment method in the request, and the row follows.
* Fixed: **the checkout block no longer asks for the street, town and postcode twice.** Where the plugin owns the address fields, the classic checkout drops WooCommerce's own street, town, region and postcode fields - the courier's fields are the address, and the order's address is written from them. The block kept WooCommerce's fields, required: a customer typed the town and the street once for WooCommerce and once for the courier, and the first was overwritten by the second. Hidden on the block now, as on the classic form; the country stays.
* Fixed: **on the checkout block, WooCommerce's street, town and postcode fields could come back when another plugin read the country locale early.** The hide above turns on a check that reads WordPress's queried page, and that is nothing until the main query has run. WooCommerce caches the country locale the first time anything reads it, so a plugin reading it on an early hook (init, wp_loaded - a common thing to do) had the fields decided before the page was known, the wrong answer stuck for the whole request, and the block asked for the street, town and postcode a second time (measured 2026-09-14 on dev: an init read of get_country_locale() brought address_1, city and postcode back on the block checkout; the same read left My Account's address form and the cart's estimate untouched). The block checkout is worked out from the requested URL when the query is not ready yet, so the answer is the same whenever it is asked - and it stays tied to the block's own page, so it is never the hide that strips the address fields off My Account or the cart.
* Fixed: **the checkout block asks for the phone as required.** A courier label needs a number for the recipient, and the classic form has always required it; the block printed "Phone (optional)" - the shop's default for the block - let the order go without one and showed the plugin's refusal at the very end. Required now, where the plugin owns the address fields, and validated by the block itself.
* Fixed: **on the checkout block, a house number typed a moment before "Place Order" could be refused as missing.** The courier fields are saved to the session as they are filled; the classic checkout holds the order until that save lands, the block did not - 70 ms between typing and the button and the order came back "Please enter a street and number" with the number on the screen. The block's checkout now waits for the save.
* Fixed: **on the checkout block, a delivery the customer pays the courier for read "Speedy  БЕЗПЛАТНО".** The classic checkout's "~3,06 €" and "paid to the courier on delivery" are added by label filters the block never runs. The rate now carries the line the block prints beside the price: "БЕЗПЛАТНО - ~3,06 € се плащат на куриера при получаване".
* Fixed: **the "track this parcel" links on BOX NOW and Sameday orders led nowhere.** BOX NOW's pointed at tracker.boxnow.bg, a host that does not exist; Sameday's at a page that answers 404. Each now opens the courier's tracking page with the number filled in (boxnow.bg/track, sameday.bg/status-na-pratkata). Every courier's link was opened in a browser with a real waybill on 2026-09-13 and is pinned by a test.
* Fixed: **an Econt refusal that keeps its words one level down is said in those words.** An address Econt cannot place comes back as HTTP 517 with an empty message and the reason inside `innerErrors` ("Информацията, която попълнихте за адрес, е недостатъчна..."); the order note showed the whole body, twelve lines of JSON. The inner messages are read now, as deep as they go.
* Fixed: "Sync now" retires Express One's kept street lists too - they were kept for a day under a key a sync could not reach.
* Faster: **Econt's street list for a town is fetched once a day, not on every keystroke.** Econt's street lookup takes no term and answers with the town's whole list - Sofia's is 4047 streets, 0.4 s - and the checkout fetched it again for every letter typed in the street box, for every address label and for every map pick. "Sync now" retires the kept lists, like the office lists.
* Fixed: **the town search lists a town that begins with what was typed before one that merely contains it.** With the town lists preloaded (the default) the search runs in the browser, and it showed matches in the order they were stored: "Ст" listed Костенец, Костинброд, Кюстендил and Силистра before every town beginning with Ст - Стара Загора was not in the first five, and Sameday opened with "Алеко Константиново". Towns beginning with the term come first now, then those with a word beginning with it ("Загора" finds Стара Загора), then the rest; and the list is cut to 200 only after that ordering, so a late-alphabet town is never pushed out by two hundred that contain the letters.
* Fixed: a tracking note no longer quotes the courier's words when they are the stage label itself - every Sameday order read `Sameday - Създадена товарителница: „Създадена товарителница“`.
* Fixed: **switching the plugin off now takes its scheduled runs off WP-Cron, and uninstalling clears the label retries too.** After deactivation the weekly nomenclature sync, the daily price refresh and the tracking poll stayed scheduled (WordPress re-schedules a recurring event from the interval stored in it, plugin or no plugin); and uninstall cleared each hook without arguments, which leaves every event that carries one - each label retry and each dispatch-day appointment carries its order id. A deactivation hook clears every event of every hook now, and uninstall calls the same code; re-activation schedules the runs again.
* Fixed: **clearing "Checkout dropdown results" gave 5 results, not the default 20.** The field's default moved from 5 to 20 in July; the sanitiser that catches an empty or invalid value still wrote 5. It writes the same default the field shows now.
* Changed (internal, nothing a merchant sees): **the settings readers and the settings screen are two classes.** `BGCouriers_Settings` keeps the readers the checkout asks on every request; the WooCommerce tab's field renderers, credential hints and AJAX moved to `BGCouriers_Settings_Admin`, loaded in wp-admin only - a checkout request no longer parses seven hundred lines of admin screen to read a setting.
* Changed (internal): **six things the settings knew about particular couriers are asked of the courier.** The "how do I get credentials" hint, whether tracking arrives by webhook (BOX NOW), whether the delivery can be billed to the recipient (everyone but BOX NOW), the default for paying cash on delivery out by ППП (Speedy, Econt), the logo file, and the settings tab row itself all come from the courier adapters and the registry now instead of lists of courier ids kept a file away - the lists that let Express One arrive with five settings that did nothing. No answer changed for any courier.
* Changed (internal): **the last of BOX NOW's widget is gone from the order data.** `_bgcouriers_boxnow_name` / `_bgcouriers_boxnow_addr` - the name and address the widget used to hand over - are written by nothing since the locker is read off the nomenclature by its id; the session keys and the order editor's fields for them are gone too. Existing orders keep what they have, and the two keys stay in the waybill fingerprint so that no live shipment is re-issued over a fingerprint that merely changed shape.

## 0.4.8
* Changed: **BOX NOW has the same checkout block as every other courier.** It was the one courier with a block of its own - BOX NOW's map widget in an iframe (`map.boxnow.bg`): a different window, centred on Athens, asking the browser for a location, unable to take the town the customer had already named for the other couriers or on the combined map, absent from that map, and edited on the order screen through three bare text boxes (owner, 2026-09-12: "boxnow works very badly ... may we have it unified with other couriers?"). BOX NOW publishes no town list, but every locker it returns carries its town (`addressLine2`) and a postal code, so the sync now reads the towns off the lockers - one per town name, with a stable id hashed from the name and, for the code, the one the shop's other couriers list the town under (Sofia's lockers start at 1111 where everyone else says 1000; the lowest locker code stays for a town only BOX NOW serves) - and stamps each locker with its town. From there BOX NOW takes the path every courier takes: the town and locker selects, the courier's own map, the preloaded town search, the combined map (its colour was already there), the town carried across couriers - which now falls back from the postal code to the town's name, because BOX NOW may list Sofia under a district code where the others use 1000 - and the order editor's town and locker fields. The locker's name and address on the order come from the nomenclature by its id; the delivery request is unchanged (`destination.locationId`). The wildcard "Any-APM" origin BOX NOW returns among its destinations is no longer offered as one. What goes with the widget: its live "limited availability" colouring per locker, which the destinations API does not expose.
* Changed: **a plugin update refreshes the courier nomenclature once, a minute after it lands.** A version can read a courier's lists differently (this one gives BOX NOW towns), and the weekly sync could be days away; an install updated from 0.4.7 would have offered BOX NOW with no town to pick until then. Not on a fresh install, where the first "Sync now" is part of setting a courier up.
* Fixed: **a sync now retires every town's cached office list.** The checkout caches a town's list for six hours, and nothing could clear those (transients cannot be deleted by prefix, and on a shop with an object cache they are not in the database): a town went on answering with a stale list through syncs and deploys. The cache key carries the courier's nomenclature generation now, which every sync renews.
* Fixed: **the X on the town now clears the office too, and the checkout knows about it.** WooCommerce's selectWoo is a fork of Select2 4.0.3, and that build relays exactly eight events - open, opening, close, closing, select, selecting, unselect, unselecting - so the checkout's two `select2:clear` handlers (town and office) had never run once, on dev or on the live shop (byte-identical file under WooCommerce 10.4.4 and 11.0.1). Measured 2026-09-12: the X emptied the town on screen and nothing else happened - the office stayed in its field, the session kept both, the price row went on quoting for the town, and the next save sent the office without its town. That half-selection then rendered as one office, greyed out for want of a town, with no list to open, until a courier switch re-rendered the block from the session (the owner's report). Three changes: the clears are bound to `select2:unselect`, which every Select2 build fires; the block never renders an office without a town; and the office field's enabled state follows the town field (as the map button already did) instead of being decided once per render, so a recalculation that ran before the session held the town no longer leaves a disabled field for the map hand-over to fill. The hand-over itself now saves the town and the delivery type in one request instead of two 2ms apart, of which the first carried no town and could land last.
* Added: **the automatic waybill can wait for the day the order ships.** Orders carrying a dispatch day - the Order Delivery Date plugin's "ship on" date, shown at the checkout - had their waybill issued the moment they reached the auto-label status. Measured on a live shop on 2026-09-12: four Speedy shipments registered on 4, 6, 9 and 11 September, all still "information received" a week later, for orders that all said they ship on 2 October (a closure the shop had set) - each a live shipment at the courier for a parcel that did not exist yet, and the customer's page saying "track this parcel" the whole time; on 2026-08-26 the same gap sent a Sameday courier to a parcel nobody had packed. The same shop also shipped one order straight through that closure, so whether the day is honoured is the shop's to say: a new General setting, **Wait for the dispatch day**, schedules the waybill for 07:00 on the dispatch day (the `bgcouriers_dispatch_hour` filter moves the hour); the order carries a note and the shipment panel shows the appointment; the Update button on the order moves the appointment with an edited day; and an order cancelled, refunded, never paid or completed by hand in the meantime ships nothing when its day comes - the trigger status itself is never in the way. Any other source of a dispatch day answers through the `bgcouriers_dispatch_time` filter. Orders without a dispatch day are issued at once, and so is every order on a shop that was already running, until it ticks the box (new installs start with it on). Generating by hand is never held back.
* Fixed: **a BOX NOW refusal is said in words.** BOX NOW turns a request down with a bare code - `{"code":"P411","status":400}` - and that JSON is what the order screen showed. The codes are documented (its Partner API manual, chapter 5), so the ones a shipment from this plugin can meet are said in words the merchant can act on, with the code kept on the end for BOX NOW support: P411 is an account not allowed to collect cash on delivery (measured on 2026-09-13; the request itself is the one BOX NOW's own plugin sends), P410 an order number already used, P405 a phone not in international form, P402 a locker BOX NOW does not know, P420 a parcel past cancelling. A code the manual does not list is shown as it came.
* Fixed: **tracking is checked for every parcel in flight, not the oldest forty.** Each tracking run asked about one batch of forty shipments, oldest first, and that was the run - so a shop with more parcels out than that never had the newer ones checked until the older ones finished. A run now goes on in batches until nothing is left or its time budget (20 seconds) is spent. On shops using the classic order storage the same query also stopped WooCommerce logging a notice on every run.
* Fixed: **a refused cancel, and a refused credential check, now say what the courier said.** "The courier did not cancel the waybill" was all a merchant read whatever the reason - already collected, handed to the driver, a login the courier turned down - and "Invalid credentials" covered a wrong password and a courier that was simply down alike. Every courier's own words now reach the order note, the shipment panel and the settings screen; Sameday's and BOX NOW's token refusals carry the reason too. The shipment panel also names the action that failed instead of calling every failure a generation.
* Fixed: **"Sync now" reported a refused login as a success.** A courier that turned the credentials down was shown as "✓ 0 cities, 0 offices, 0 rates", the same as a courier with nothing to fetch. A sync that fetched nothing now says so, in the courier's own words - Speedy's refusals in particular were being read as an empty country - and a sync that refreshed the towns but was refused every price says which. Express One's refusal read "Array"; Econt's and Pigeon's arrived as raw JSON. All seven now refuse in words.
* Fixed: **"Request the courier" never sent one.** The confirm button on the "Request a courier" screen answered "The link you followed has expired" every time, since the screen was added in 0.3.7: the form's security token and the page's own were posted under one name and overwrote each other. It reaches the courier now. And what it sent Speedy would have been refused too - the pickup moment was written without a time zone, which Speedy insists on - so that is written with the shop's zone. A confirmation is also sent once now, however many times the same one arrives (a refresh of the result, a second click while the courier is answering), and the result is shown on its own page.
* Fixed: **a notice on every request on sites with debugging on.** The couriers' names were asked for as translations while the plugin was still loading, which WordPress 6.7 and later flag as too early - and on a site that shows notices, that one landed before the login cookie could be set. Brand names are not translated; they are plain names now.
* Fixed: **"Request a courier" offered tomorrow while the courier still came today.** The screen judges whether the courier's cut-off has passed, and it did that against a clock WordPress hands back shifted by the site's time zone - three hours ahead in a Bulgarian summer. From 14:00, with the cut-off at 17:00, the day offered was tomorrow, next to a line still saying the courier accepts requests until 17:00. Both now read from the real clock and from the same list of cut-offs still ahead, so they agree.
* Fixed: **a waybill the courier accepted but did not fully apply is now flagged on the order screen.** When a courier creates the shipment but quietly drops part of what was asked - Speedy can accept a waybill and not apply the cash on delivery - the order got a note, and a flag meant for the order screen that the screen never showed. The note scrolls away under the next one; the parcel is on the desk about to be handed over. The warning now sits on the order's shipment panel until the waybill is re-issued.
* Fixed: **a BOX NOW parcel's progress never reached the orders list.** BOX NOW reports through its own notifications rather than being polled, and those were written to the order in a form nothing displayed - so a BOX NOW order showed a blank where its tracking belonged, was never marked finished, and was never moved on automatically when delivered. Its updates now land exactly where the other couriers' do, and a notification BOX NOW sends twice is recorded once.
* Fixed: **an order whose waybill was cancelled went on showing as "registered" in the orders list.** The shipment's stage was recorded the moment a waybill was issued and was left behind when the waybill was voided. A voided shipment now leaves nothing on the order but its note.
* Fixed: **an order could end up with two shipments booked at the courier.** Two ways. The waybill was written to the order only after the label PDF had also been fetched, and when that second call failed moments after the first had succeeded, the shipment existed at the courier but not on the order - so the automatic retry booked another, and the first was never voided. And nothing stopped two requests for the same order at the same moment - the payment confirmation's automatic label and a click on the order screen - from each booking one. The waybill is now recorded the instant the courier issues it, the PDF is fetched on a best-effort basis with a note when it cannot be, and an order is claimed before its waybill is made, so a second request is told to wait rather than handed a second shipment.
* Fixed: **one courier with a faulty connector could stop tracking updates for every courier.** Tracking is checked in batches of forty orders, oldest first, and a connector that broke on one order's answer ended the whole batch - every order behind it, whichever courier it was with, went unchecked. Since that order was never marked finished it was at the front of every batch, so tracking for the whole shop simply went quiet. The same fault could end the weekly courier sync for the couriers behind it, and on the checkout it could show an error page instead of the fallback price. A faulty connector is now noted in the log and skipped, and the rest carry on.
* Fixed: **a courier that failed to answer once could grey out both delivery options for a town for six hours.** The checkout asks two things about a chosen town - which offices it has, for the dropdown, and which kinds of delivery it offers, for the tabs - and asked the courier twice for the same list, keeping two separate copies. Only the first had been taught not to remember a failed answer. The tabs are now read off the very same list as the dropdown, so a town is asked about once, the two can never disagree, and a courier that is down for a moment is simply asked again next time.
* Fixed: **a delivery price could be shown in a currency the shop no longer uses.** Prices are remembered for a few hours so the checkout stays quick, and what was remembered was the number without the currency it was quoted in - so a shop changing from lev to euro went on asking for the lev figure in euros, nearly twice the real cost, until each remembered price ran out. The daily reference price behind the courier list had the same gap, and it lasted until the next sync. Every remembered price now carries its currency, and one quoted in a currency the shop has stopped using is not used at all - the price the merchant configured is shown instead.
* Fixed: **the delivery price recorded on an order belonged to whichever courier was priced last, not the one the customer chose.** WooCommerce prices every courier in the zone on every recalculation and they all wrote to one place. It is kept per courier now, so the order carries what its own courier quoted and whether that was a live price or a fallback.
